1. Fresh llama.cpp installation, real LFM2/LFM2.5 generation, switch models and unload. Installed state must match executable files; only intended sessions remain; API behavior must agree with the UI.
2. Settings cancellation, numeric validation, persisted values, staged changes and explicit reload. Check actual engine process arguments and PID before/after; Save alone must not silently replace a running engine when the UI promises next load.
3. Explicit switching matrix: model A→B→A on llama.cpp, same model across engines and back, then failure/recovery during a switch. Compare API model lists, live processes, selected provider, preserved chat turns and each provider’s own saved settings.
4. Recover from a deliberately invalid extra argument. Failure must show a useful error/log and permit correcting the settings and loading again. Two clients must not silently overwrite settings protected by revisions.
5. Install other locally supported engines, inspect compatibility and load a compatible model when available. Check updates/repeated actions, active-build removal protection and persistence across server restart.

Budget: one focused session of approximately 45–60 minutes, with a 90-minute maximum including tool/network waits. No subagents. Interactive browser control chooses actions from current UI state; backend/CLI reads verify durable data and real processes. Browser-agent sampling controls are not separately exposed by the tool.
