# 2026-10-23 — Gate inference and keep downloads visible

- **Context:** Web and terminal clients share the same model jobs, but a running management server or a downloaded file does not mean inference is ready. Download progress formerly consumed the top of several screens. A pending first model needs a final waiting screen that does not trap the user.
- **Decision:** Both clients use a shared readiness selector. Start and chat submission require an appropriate ready model session; chat also requires the API listener. Workspace service admission checks enforce the same conditions. Management, download, cancellation and stop operations remain available. Missing models lead to acquisition; in-progress work shows a concise waiting reason after Start or Send is pressed. Send remains available when a draft exists, and a blocked attempt preserves it. Web opens its model picker for acquisition; the terminal routes to the model catalog without clearing the draft. Both clients keep a compact download card at the bottom right, with a detailed download dialog and existing pause/remove confirmations. Terminal popups temporarily cover the card completely rather than exposing partial controls behind them.
- **Decision:** The final onboarding screen offers Minesweeper using shared rules, an explicit Continue in background action and an optional email field with a Confirm action. Continuing completes onboarding and opens the chosen server page while download status remains visible. A finished download never silently starts inference.
- **Email PR requirement:** The email field is intentionally a **mockup**, as requested by the owner. It stores its value only in the current client view and neither sends nor registers an email subscription. The requested UI uses idle, invalid, confirming and confirmed states, ending with the truthful “Email saved” message; it does not claim a notification was sent. The future PR must explicitly call out that an email notification delivery service still needs to be configured and implemented. Do not present email delivery as completed. A real implementation needs durable per-download subscription state, verified delivery configuration, consent and cancellation, retry/error handling, and delivery tests before delivery can be enabled.
- **Endpoint isolation:** An unconfigured terminal chat endpoint follows this workspace’s configured local listener instead of silently using port 1337. Explicit endpoint overrides remain independent. Empty model IDs are rejected before conversation creation or network requests, including remote endpoints; equivalent loopback addresses use the same local readiness and service admission checks.
- **Cloud routing:** Configured cloud chat models appear as ready routes without a local engine session. Snapshots contain model/provider identifiers only, not cloud headers or credentials. Streaming and non-streaming chat verify the core’s selected-provider map and registration order, refusing an explicit provider that would route elsewhere.
- **Consequences:** A model can download while the user configures the server. Model readiness is enforced again at the shared operation boundary. This check does not change the background management daemon's lifecycle or remote endpoint ownership. Browser and terminal Minesweeper support keyboard and mouse, including flags, restart, first-click safety and win/loss states.
- **Alternatives:** Blocking all navigation until the download finishes would prevent configuration during large transfers. Starting the listener regardless of model state or silently redirecting every failed request would obscure readiness. Actual email transport was explicitly deferred by the owner.
