# 2026-11-04 — Pin core 0.21.3 and keep atc's report tags

- **Context:** Core 0.21.1 carries the tensor-count correction the server patched into 0.21.0 (atomic-chat-core#67) and rebuilt Sentry reporting around its own diagnostic vocabulary (atomic-chat-core#70); 0.21.2 makes Windows GPU loads survive builds a card cannot run (CUDA 13 gate, one retry on the next build, CUDA runtime delivery, pack smoke test, registry GPU probe; atomic-chat-core#75). On 0.21.2 every atc report reached Sentry as `component: core`, `operation: event`, without atc's codes (`ATC_*`, `HF_HTTP_*`, `PROXY_CONFIG_INVALID`) or its finite diagnostic tags, and a bad proxy setting was reported as an unknown download failure. A failed load's details also end with the core's `atomic-core-diag {…}` line now, and the core tags FAT32's 4 GiB limit `disk_fs_limit`.
- **Decision:** Pin `@atomic-chat/core` 0.21.3 exactly, which lets a host name its own report tag keys (`hostTagKeys`, core ADR `2026-11-04-let-a-host-keep-its-own-report-tags`). atc passes `component`, `operation`, `failure_reason`, `native_failure`, `diagnostic_code` and `diagnostic_cause_code`, reads its own error codes beside the core's (`src/telemetry/codes.ts`), and gives download reports a core diagnostic (`downloads`/`download`, reason) instead of the fingerprint the core no longer reads. Drop the package patch and `patchedDependencies`. Text for people (`describeError`, the terminal UI) leaves the diag line out; `--json` and the admin API keep it. atc's downloader, lifted from the core, tags EFBIG and a failed write that ends past 4 GiB − 1 as `disk_fs_limit` and says to move the data folder; such a failure is not reported, like `disk_full`.
- **Consequences:** Messages no longer reach Sentry at all: an atc event is named `<component> <operation>: <reason>` and grouped by the core's fingerprint with atc's part in it. Model-download renames are not retried on Windows, as in the core. No engine ran and no Windows machine was used in these checks.
