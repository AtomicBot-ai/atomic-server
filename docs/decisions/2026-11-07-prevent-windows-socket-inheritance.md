# 2026-11-07 — Package a runtime that does not inherit Windows sockets

- **Context:** In the Windows preview built with Bun 1.3.14, an engine spawned after the API inherited its listening socket. `server.close()` completed, but rebinding the port failed while the engine lived. Avoiding unnecessary restarts in Connect reduced the symptom but could not repair an explicit API restart. Bun fixed socket creation and accepted-socket inheritance in [oven-sh/bun#36938](https://github.com/oven-sh/bun/pull/36938), closing [#36936](https://github.com/oven-sh/bun/issues/36936).
- **Decision:** Pin atc's compiler and embedded runtime to Bun 1.4.4 in `.bun-version`, matching core's current CI/release runtime. Both atc workflows read that file, including the Windows baseline compiler. `scripts/build-binaries.mjs` refuses a different compiler on PATH before producing any artifact. Application code continues to use only Node APIs; no FFI, runtime branches, or engine restarts are introduced.
- **Consequences:** The runtime prevents inheritance at socket creation; the core can close and recreate its API while the same engine process stays alive. A local/global Bun upgrade is not performed automatically. Builders must put the pinned version on PATH. This changes the embedded runtime for all release targets; this task runs only focused socket/build checks and the Windows acceptance scenario, not a full release matrix.
- **Regression:** One portable fixture starts HTTP, spawns a child that opens no sockets, closes HTTP, rebinds the same port and serves another response while the original child remains alive. Runtime compatibility tests execute it under Node and Bun; a compiled e2e test covers native executables. The fixture also reproduces the failure on the old Windows runtime and cleans up its child and sockets on failure.
- **Evidence (2026-11-07):** The identical compiled fixture on Windows failed with `EADDRINUSE` under Bun 1.3.14 and passed under 1.4.4. The focused runtime test passed on macOS under Node 22 and Bun 1.4.4; its compiled e2e and the seven compiler-guard cases passed. On the user's Windows preview, `llamacpp-upstream` loaded the existing `unsloth/Qwen3-0.6B-Q4_K_M`; an actual `api.restart` rebound port 1339 with the same engine PID (27844), followed by successful model-response verification and API ping. The deployed binary SHA-256 is `f7964f5736f6d93f5f0ec0fe0903360980ade74299352e6781add5d0b5cf8b07`. Review found no issues. No full suite or release matrix was run.
- **Alternatives:** Disabling port checks would leave the socket occupied. Unloading models or wrapping every engine spawn would interrupt inference or duplicate runtime process management without fixing the underlying inherited handles. A patched custom runtime or native handle manipulation is unnecessary because the upstream fix is already released.
